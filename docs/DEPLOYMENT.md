# Deployment — putting Saksham IQ live

Three pieces, three hosts, and the whole thing is free to start:

| Piece | Host | What it is |
|---|---|---|
| Database | **Neon** | Managed PostgreSQL, free tier, always on |
| API | **Render** | The `backend/` FastAPI app, built from `backend/Dockerfile` |
| Web app | **Vercel** | The `frontend/` Next.js app |

The mobile app is not deployed by any of this; it points at whatever
`API_BASE` it is built with.

Order matters: the database first (the API will not start without it), then
the API (the web app needs its URL at *build* time, because
`NEXT_PUBLIC_API_BASE_URL` is baked into the bundle), then the web app, then
one CORS value back on the API.

---

## 1. Database — Neon

1. <https://neon.tech> → sign in with GitHub → **Create project**.
   Region: `AWS ap-southeast-1 (Singapore)` — nearest to the Render region below.
2. Copy the **connection string**. It looks like:

   ```
   postgresql://neondb_owner:XXXX@ep-xxx-xxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require
   ```

   Paste it exactly as Neon gives it. `app/db/session.py` rewrites
   `postgresql://` to `postgresql+psycopg://` itself, so nothing needs editing.

Nothing else to do here: the API container runs `alembic upgrade head` on every
boot, so the schema is created on the first deploy and migrated on every one
after it.

## 2. API — Render

The repo carries a blueprint, so this is not clicked together by hand.

1. <https://render.com> → **New** → **Blueprint** → connect the GitHub repo
   `Rupadi-International/kindergarten` → it finds [`render.yaml`](../render.yaml).
2. Render asks for the three values marked `sync: false`. Fill in:

   | Key | Value |
   |---|---|
   | `DATABASE_URL` | the Neon string from step 1 |
   | `GROQ_API_KEY` | a key from <https://console.groq.com/keys> |
   | `CORS_ORIGINS` | leave as `http://localhost:5000` for now; fixed in step 4 |

   `JWT_SECRET` and `POLICY_ADMIN_TOKEN` are generated by Render — do not set
   them by hand and do not put them in the repo.
3. Deploy. The first build is ~3 minutes. When it is up:

   ```
   curl https://saksham-iq-api.onrender.com/health
   ```

   Note the service URL — the web app needs it next.

**The free plan sleeps.** After 15 idle minutes Render stops the instance and
the next request waits ~50 seconds for it to wake, which a four-year-old will
experience as the app being broken. `plan: starter` in `render.yaml` (about
$7/month) is what stops that; the free plan is fine for showing somebody the
app, not for a child using it daily.

### What is deliberately *not* installed

`backend/requirements-prod.txt` is `requirements.txt` minus `sentence-transformers`,
which pulls torch (~2GB) in with it. `app/playground/rag.py` imports it inside
the function that builds the embedding index and falls back to keyword search
when that fails, so the AI Teacher still retrieves and still teaches — just by
keyword. On an instance with 2GB of RAM to spare, add
`sentence-transformers>=3.0,<6` back to that file and the index builds itself
at boot.

## 3. Web app — Vercel

1. <https://vercel.com> → **Add New** → **Project** → same GitHub repo.
2. **Root Directory: `frontend`.** This is the one setting that is not in a
   file, and the build fails without it. Framework is detected from
   [`frontend/vercel.json`](../frontend/vercel.json).
3. Environment variable:

   | Key | Value |
   |---|---|
   | `NEXT_PUBLIC_API_BASE_URL` | `https://saksham-iq-api.onrender.com` (no trailing slash) |

   `NEXT_PUBLIC_*` is baked into the bundle at build time, so changing it later
   needs a **redeploy**, not a restart.
4. Deploy. Note the domain, e.g. `https://kindergarten-xyz.vercel.app`.

## 4. Close the loop — CORS

Back on Render → the service → **Environment** → set:

```
CORS_ORIGINS=https://kindergarten-xyz.vercel.app,https://www.your-custom-domain.com
```

Comma separated, scheme included, no trailing slash, no `*` — the API sends
credentials, and `allow_credentials=True` with a wildcard origin is refused by
every browser. Save; Render restarts the service.

This is the classic failure of this stack: the API answers `curl` perfectly and
every request from the browser fails. If the web app says it cannot reach the
learning server, check this value first.

## Environment variables, in one place

| Key | Where | Required | Note |
|---|---|---|---|
| `DATABASE_URL` | Render | **yes** | Neon string; `postgres://` and `postgresql://` are both accepted |
| `JWT_SECRET` | Render | **yes** | Generated by the blueprint. No default exists: unset means sign-in refuses rather than signing with something guessable |
| `ENV` | Render | yes | `production`. Development is what relaxes the two rules above |
| `CORS_ORIGINS` | Render | **yes** | The Vercel domain(s), comma separated |
| `GROQ_API_KEY` | Render | no | Without it the teacher falls back to deterministic words — it still teaches |
| `LLM_PROVIDER` | Render | no | `groq`, or `none` to run the whole app with no model at all |
| `POLICY_MODE` | Render | no | `shadow`. Do not ship `on` until `app/policy/evaluate.py` says the learned policy is better |
| `POLICY_ADMIN_TOKEN` | Render | yes | Generated. `POST /policy/disable` refuses without it outside development |
| `PLANNER_AUTO_RUN` | Render | no | `1`, so a plan is frozen before the child opens the app |
| `NEXT_PUBLIC_API_BASE_URL` | Vercel | **yes** | The Render URL. Baked at build time |

## After the first deploy

- **A parent has to sign up.** There is no seeded account, and
  `parents.consent_granted_at` is written by the parent surface only — DPDP and
  COPPA both want an explicit act by a person, so nothing automates it.
- **The first day's plan** is frozen by `planner_runner`'s sweep within
  `PLANNER_INTERVAL_SECONDS` (15 minutes) of the child being created, or by the
  child's first request if it gets there first.
- **A schedule change is invisible until tomorrow.** Plans are frozen per child
  per day. To see a change today, delete today's `daily_plans` rows and let them
  re-freeze.
- **Logs**: Render → service → **Logs**. The boot lines to look for are
  `alembic upgrade head`, and — if anything is wrong with the schema — the
  explicit "Database is N migration(s) behind" error, which is what a silently
  missing schedule looks like from the inside.

## Running the whole thing locally in Docker

The same image, against a local Postgres:

```sh
docker build -t saksham-api ./backend
docker run --rm -p 8008:8008 \
  -e DATABASE_URL='postgresql://user:pass@host.docker.internal:5432/saksham' \
  -e JWT_SECRET='dev-only-not-a-real-secret' \
  -e CORS_ORIGINS='http://localhost:5000' \
  saksham-api
```

`python backend/run.py` remains the ordinary way to develop; it exists because
of two Windows-shaped problems the container does not have.
